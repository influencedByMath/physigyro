**One-paragraph summary.** Drone flight controllers remove motor vibration noise from the gyroscope signal with a stack of digital filters (lowpass filters and notch filters). Every filter adds delay, and delay reduces the stability margin of the control loop. Too little filtering sends noise to the motors, which makes them hot and wastes battery. Today pilots tune these filters by trial and error. This project (1) builds an exact frequency-domain model of the full filter stack inside the attitude control loop, (2) formulates filter tuning as an optimization problem that maximizes stability margin under a motor-noise limit, and (3) trains a small machine-learning model that predicts the optimal settings instantly from a measured noise spectrum. A physics-based safety check verifies every ML prediction. The model is trained on optimizer-generated labels, tested on real noise from public PX4 flight logs, and exported to C so it can run on a flight controller.

## 3. The problem and why it matters

**What happens inside a flight controller.** The gyroscope measures how fast the drone rotates. Motors and propellers shake the frame, so the gyro signal contains vibration noise, mostly at the motor rotation frequencies and their harmonics. The flight controller must remove this noise before the PID controller uses the signal. It does this with a chain of digital filters.

**The trade-off.**

- Every filter delays the signal a little. The control loop needs enough *phase margin* to stay stable, and delay eats phase margin. Too much delay causes oscillation, "propwash" wobble, or a crash.
- Too little filtering lets noise pass through the PID controller to the motors. The D-term is the worst, because it amplifies high frequencies. Result: hot motors, wasted battery, shaky video, shorter motor life.

**How it is done today.** Pilots and engineers tune filter cutoffs by trial and error, using hobby guides, Blackbox or Flight Review plots, and experience. Firmware defaults are chosen to be "safe for most drones", so they often filter more than needed. A closed commercial tool (FPVTune) uses a neural network trained on human tunes, with no stability guarantee.

**Why ML and not only an optimizer.** A full optimization needs too much computation to run on a flight controller in real time. A small trained model can predict near-optimal settings in microseconds. This makes *in-flight retuning* possible, for example when noise changes because the battery voltage drops, a propeller is damaged, or the payload changes.

**Real-world impact.** Applies to hobby FPV drones (Betaflight) and to professional drones for inspection, agriculture, mapping, delivery and rescue (PX4, ArduPilot). Better filtering means more stable flight, cooler motors, longer flight time and less tuning effort.

## 4. Background: how flight controllers filter gyro data

### 4.1 Signal path (one axis)

```text
               +------------------------ gyro filter stack F_g -------------------------+
raw gyro  -->  | notch filters (static, ESC-RPM based, FFT based) --> gyro lowpass filter | --> filtered rate --> P and I terms
               +---------------------------------------------------------------------------+
                                                  |
                                                  +--> derivative --> D-term lowpass F_d --> D term

P + I + D --> mixer --> ESCs --> motors and propellers --> body rotation --> gyro (the loop closes)
```

**Checked 2026-10-10** (PX4 v1.16.0 `VehicleAngularVelocity.cpp`, same in v1.14 to main): the D-term path differentiates the gyro **after** the notches **and** the gyro lowpass (`FilterAngularVelocity` filters the sample array in place, then `FilterAngularAcceleration` differentiates the same array). Confirmed on real data in the feasibility test (`experiments/feasibility/`): the "D before the lowpass" model is 20-36 dB off, the PX4 model within 1 dB.

### 4.4 Filter mathematics (implement in `src/filters.py`)

Notation: sample period $T_s = 1/f_s$, evaluation frequency $f$, $z = e^{j 2\pi f T_s}$.

**PT1 (first-order lowpass), Betaflight form**

$$k = \frac{2\pi f_c T_s}{2\pi f_c T_s + 1}, \qquad y_n = y_{n-1} + k\,(x_n - y_{n-1}), \qquad H_{PT1}(z) = \frac{k}{1 - (1-k)z^{-1}}$$

**PTn (n PT1 stages in series)**

$$H_{PTn}(z) = \big[H_{PT1}(z;\ c_n f_c)\big]^n, \qquad c_n = \frac{1}{\sqrt{2^{1/n} - 1}} \quad (c_2 = 1.5538,\ c_3 = 1.9615)$$

**PX4 D-term lowpass (`AlphaFilter`)** is the PT1 above with $k = T_s/(\tau + T_s)$, $\tau = 1/(2\pi f_c)$, running at the FIFO rate (checked 2026-10-10).

**2nd-order Butterworth lowpass (PX4 gyro filter).** Bilinear transform with pre-warping. Let $K = \tan(\pi f_c T_s)$ and $D = 1 + \sqrt{2}K + K^2$:

$$b_0 = \frac{K^2}{D},\quad b_1 = 2b_0,\quad b_2 = b_0,\qquad a_1 = \frac{2(K^2 - 1)}{D},\quad a_2 = \frac{1 - \sqrt{2}K + K^2}{D}$$

$$H(z) = \frac{b_0 + b_1 z^{-1} + b_2 z^{-2}}{1 + a_1 z^{-1} + a_2 z^{-2}}$$

**Notch filter (2nd order).** Analog prototype, discretized with the bilinear transform pre-warped at $f_0$ (test against `scipy.signal.iirnotch`):

$$H(s) = \frac{s^2 + \omega_0^2}{s^2 + \frac{\omega_0}{Q}s + \omega_0^2}, \qquad Q = \frac{f_0}{BW} \quad \text{(PX4 gives bandwidth } BW \text{ in Hz)}$$

Betaflight's static notch uses a centre $f_0$ and a lower cutoff $f_{cut}$: $Q = \dfrac{f_0 f_{cut}}{f_0^2 - f_{cut}^2}$.

**ESC-RPM notch bank.** For each motor $i$ (4 motors) and harmonic $h = 1 \dots H$, place a notch at $h \cdot f_{m,i}$, where $f_{m,i}$ is the rotation frequency of motor $i$ in Hz (RPM / 60). The bank is the product of all notches:

$$H_{bank}(z) = \prod_{i=1}^{4}\prod_{h=1}^{H} H_{notch}(z;\ h f_{m,i},\ Q)$$

**Phase lag and delay.** Phase lag at frequency $f$: $\varphi(f) = -\angle H(e^{j2\pi f T_s})$. Equivalent delay: $\tau(f) = \varphi(f) / (2\pi f)$.

**Rules of thumb (valid for $f$ well below the cutoff).** Use them as sanity checks for the code.

| Filter | Approximate delay | Example |
|---|---|---|
| PT1 at $f_c$ | $\dfrac{1}{2\pi f_c}$ | 100 Hz gives 1.6 ms |
| 2nd-order Butterworth at $f_c$ | $\dfrac{\sqrt2}{2\pi f_c}$ | 40 Hz (PX4 gyro default) gives 5.6 ms |
| PX4 D-term PT1 at $f_c$ (in addition to the gyro filters) | $\dfrac{1}{2\pi f_c}$ | 30 Hz (default v1.15-v1.16) gives 5.3 ms; 20 Hz (default v1.17+) gives 8.0 ms (corrected 2026-10-10; the old values assumed a Butterworth) |
| Notch at $f_0$ with quality $Q$ | $\dfrac{1}{2\pi Q f_0} = \dfrac{BW}{2\pi f_0^2}$ | 100 Hz, BW 15 Hz gives 0.24 ms |
| ESC-RPM bank, 4 motors x 3 harmonics at $f_m$ | $\approx 4 \cdot \dfrac{BW}{2\pi f_m^2}\left(1 + \tfrac14 + \tfrac19\right)$ | $f_m$ = 100 Hz, BW 15 Hz gives about 1.3 ms |
| Sample-and-hold plus computation | about 0.5-1.5 samples | 800 Hz loop (multicopter default) gives 0.6-1.9 ms; 400 Hz gives 1.25-3.75 ms |

**Key relation: phase-margin cost of delay.** A pure delay $\tau$ costs

$$\Delta PM = 360 \cdot f_c \cdot \tau \quad \text{degrees}$$

at crossover frequency $f_c$. Example: $f_c = 10$ Hz and $\tau = 5.6$ ms cost about 20 degrees.

## 6. Research questions, success criteria and contributions

**RQ1 (physics).** How much stability margin do default and common filter settings waste, for realistic drones and real noise?

**RQ2 (ML).** Can a small ML model predict near-optimal filter settings instantly from a noise spectrum? Does it still work on real drone noise when it was trained only on synthetic noise?

**RQ3 (embedded).** Is the model small and fast enough to run on a flight controller?

## 7. Method in detail

### 7.0 Design goal: minimum noise, minimum delay, maximum stability

Every setting $\theta$ (all filter parameters together) is judged by three quantities, all defined in Section 7.2:

| Goal | Quantity | Better when |
|---|---|---|
| Minimum noise | $\tilde N(\theta)$: motor-command noise relative to the default setting on the same drone and spectrum | lower |
| Minimum delay | $\tau_F(\theta)$: delay of the gyro filter stack at the crossover frequency (and $\tau_D$ for the D-term path) | lower |
| Maximum stability | PM, GM, delay margin DM, and peak sensitivity $M_s$; worst case over the plant uncertainty set (Section 7.1.1) | higher PM, GM, DM; lower $M_s$ |

**How the three goals relate.** With the PID gains and the plant fixed, filter delay eats phase margin directly (Section 4.4):

$$PM(\theta) \approx PM_{unfiltered} - 360 \cdot f_c \cdot \tau_F(\theta) \quad \text{degrees (when } f_c \text{ moves little)}$$

So *minimum delay* and *maximum stability* point in the same direction. *Minimum noise* points the other way: lower cutoffs and wider notches remove more noise but add delay. The three goals therefore reduce to **one trade-off: noise versus delay/stability**. No setting wins all three at once without limit, so we solve the trade-off in a defined way:

- **Mode A:** maximum stability (which means minimum delay) without more noise than the default.
- **Mode B:** minimum noise without less stability than the default.
- **Mode C:** the full Pareto front between the two.
- **Hard stability limits** (PM floor, GM, $M_s$) are active in every mode and again in the safety check.

**How each part of the method serves the goal:**

| Part | Section | Contribution |
|---|---|---|
| Data-quality pipeline | 7.4.3 | Noise spectra are real, not artefacts of dropouts, clipping, aliasing or wrong axes |
| Flight-controller data from logs (RPM, parameters, high-rate topics) | 7.4.5 | Exact motor frequencies allow narrow notches (much noise removed for little delay); real settings as a fair baseline; real-data validation |
| Plant parameters (three tiers) | 7.1.1 | Realistic delay cost and realistic stability margins |
| Optimizer | 7.3 | Finds the best noise/delay/stability compromise |
| ML tuner | 7.7 | Gives that compromise instantly |
| Physics safety check | 7.8 | Guarantees the stability limits and the noise limit (within the model, robustly) |
| Time-domain and real-log validation | 7.11, E10, E11 | Checks that the compromise holds outside the frequency-domain model |

**Reporting rule:** every table or figure that compares settings shows $\tilde N$, $\tau_F$ and PM together (tables also GM and $M_s$). Never report one goal alone.

### 7.1 Control loop model (one axis: roll or pitch)

Plant, from control command to body rate:

$$P(s) = \frac{b}{s} \cdot \underbrace{\frac{1}{\tau_m s + 1}}_{\text{motor lag}} \cdot \underbrace{e^{-s T_d}}_{\text{ESC and output delay}}$$

- $b$: control effectiveness [rad/s^2 per unit command]
- $\tau_m$: motor and propeller time constant [s]
- $T_d$: extra delay from ESC protocol and computation [s]

Zero-order hold of the digital controller: $ZOH(s) = \dfrac{1 - e^{-sT_c}}{sT_c}$, where $T_c$ is the control period.

Controller feedback path, meaning everything that acts on the measured gyro:

$$C_{fb}(f) = F_g(f)\left[K_p + \frac{K_i}{j2\pi f} + K_d\, j2\pi f\, F_d(f)\right]$$

In code, use discrete-time versions of the integrator and derivative at the control rate, and evaluate each filter at the rate it runs.

Open loop: $L(f) = C_{fb}(f)\cdot ZOH(f)\cdot P(f)$.

**PX4 controller form (checked 2026-10-10 in v1.16.0 `rate_control.cpp` and `MulticopterRateControl.cpp`: the form below is right; the I sum is updated after it is used, so $I(z) = T_c z^{-1}/(1-z^{-1})$, and a nonlinear I-gain reduction acts only for rate errors above about 100 deg/s).** PX4 computes the rate-loop output roughly as $u = K\,[P\,e + I\!\int e\,dt - D\,\dot\omega_f] + FF\,\omega_{sp}$, with `MC_ROLLRATE_K`, `_P`, `_I`, `_D`, `_FF`. The D term acts on the measured, filtered angular acceleration, not on the error. The feed-forward acts only on the setpoint, so it does not change $L(f)$ and is ignored for margins. With real gains: $K_p = K P$, $K_i = K I$, $K_d = K D$.

**Tier 2: system identification from public logs (strongly recommended; on the cut list).**

Idea: some public logs record the controller output and the gyro at full rate. From the input (torque command) and the output (rotation rate) we can estimate $b$, $\tau_m$ and $T_d$ of real drones.

1. **Which logs:** fit-half logs with `SDLOG_PROFILE` bit 3 or bit 4, which give full-rate `vehicle_torque_setpoint` and `vehicle_angular_velocity`. Best are logs that also have `sensor_gyro_fifo`. Profile 273 (bits 0, 4, 8) was the most common profile among FIFO logs in the audit; one such pilot log had torque setpoint, angular velocity and motor outputs at 800 Hz and ESC status at 200 Hz.
2. **Signals:** input $u_k$ = roll torque setpoint (normalized). Output $\omega_k$ = roll rate from the raw FIFO gyro, rotated to the body frame (gate Q7), lowpass-filtered and resampled to the control rate. Raw gyro avoids having to undo the gyro filters. Without FIFO data, use `vehicle_angular_velocity` and put the known filter $F_g$ (from the log's own parameters) into the model.
3. **Select data:** in-air segments with enough excitation (standard deviation of $u$ above TBD), no motor saturation (all `actuator_motors` strictly between 0 and 1), and slow trends removed (subtract the segment mean or high-pass at TBD Hz).
4. **Model** (discrete time, control period $T_c$). Angular acceleration $\alpha_k = (\omega_k - \omega_{k-1})/T_c$. Motor lag plus delay give
   $$\alpha_k = a\,\alpha_{k-1} + b\,(1-a)\,u_{k-d} + c$$
   where $a = e^{-T_c/\tau_m}$, $d$ is the delay in samples and $c$ is a bias.
5. **Fit:** for every integer delay $d$ from 0 to TBD (candidate 20 samples), solve for $(a, b, c)$ with linear least squares (`numpy.linalg.lstsq`). Choose the $d$ with the smallest error on a held-out segment of the same flight. Then $\tau_m = -T_c/\ln a$, and $T_d = d\,T_c$ minus the ZOH and computation delay that the loop model already contains (never count a delay twice). **Feasibility test 2026-10-10: this fit failed on real closed-loop data (negative held-out VAF). A frequency-response fit with the rate setpoint as instrument worked (b = 431/474, τ_m = 29/34 ms on log b27d09e3); decided as D-14 (2026-10-14): use the rate setpoint as instrument only in Acro, the attitude setpoint in Stabilized/Altitude mode; code in `src/sysid.py` (`instrument=`).**
6. **Quality gate:** accept the result only if the variance accounted for (VAF) on the held-out segment is at least TBD % (candidate 70 %) and $0 < a < 1$. **For the frequency-response fit of D-14 this gate is replaced by (frozen with A4, D-34, D-36):** at least 6 coherent frequencies (coherence ≥ 0.5, 0.5-20 Hz, 1.28 s Welch segments), the two instruments agree within 1 dB / 5° in Position/auto modes, fit error ≤ 3 dB / 15°, $\tau_m$ off its fit bounds, $T_d$ below its 30 ms bound.
7. **Realism check (important):** combine the identified plant with the log's *real* PID gains and *real* filter settings and compute PM, GM and $M_s$. Real drones that fly well must come out stable with plausible margins (for example PM 30-75°). If many come out unstable, the model structure is wrong: stop and fix it before continuing.
8. **Output:** histograms of $\tau_m$, $T_d$, $b$, $f_c$ and PM over the identified vehicles, as a paper figure (E12). **D-36:** they informed the Tier 1 ranges and the uncertainty set but do not replace them; identified plants are a sensitivity check only, never training sources; identified real drones that also have a steady library window are the real-gain cases of Task 3.

**Tier 3: synthetic drones for the training data (core).**

1. Sample $\tau_m$ and $T_d$ log-uniformly from the Tier 1 ranges (D-28 as revised by D-36: 15-60 ms, 0.3-8 ms), the control and filter rates as an empirical pair (D-28), and the hover motor frequency from the generator's source vehicle. A drone whose chip has a fitted low-pass term gets the chip delay of D-33 (the lower bound added to the nominal $T_d$, the rest to the delay step). Identified Tier 2 plants are not sampled (D-36: sensitivity check only).
2. Choose PID gains in one of two ways:
   - **(a) Crossover design (main training set):**
     1. Sample a target crossover frequency $f_c$, log-uniform in 3-10 Hz (D-36).
     2. Write the PID as $C(s) = K_p\left(1 + \dfrac{\omega_i}{s} + \dfrac{s}{\omega_d}\right)$ with $\omega_i = 0.03 \cdot 2\pi f_c$ (D-36; was $2\pi f_c / 10$) and $\omega_d = r \cdot 2\pi f_c$, where $r$ is sampled in [0.5, 3].
     3. Solve for $K_p$ so that $|L(f_c)| = 1$ **without filters** (1-D root finding, `scipy.optimize.brentq`).
     4. Keep the drone only if its unfiltered phase margin is between 60 and 95 degrees (D-36; the p10-p90 range of the identified real drones, 62.6-95.0°; was 45-75°), like a well-tuned real drone.

     Here $b$ can be fixed to 1. Because $K_p$ is solved from the crossover condition, and noise is always reported *relative to the default settings on the same drone*, $b$ cancels out.
   - **(b) Real-gain mode (extra realism test):** take $(P, I, D, K)$ from a random real log of the fit half, and $b$ from Tier 2 (or sampled from its distribution). Here $b$ does **not** cancel, because $K_p$ is not solved from the crossover condition. An evaluation mode only (D-36: identified plants are not training sources); in practice it uses the identified real drones themselves, each with its own gains, identified plant, actual setting and library spectrum (D-15; Task 3 needs both an identification and a steady window, D-36 (6)).
3. Also require that the drone with its own default filters meets the nominal limits: PM $\ge$ 30° (D-30), $M_s \le 2.0$ (D-31) and GM $\ge$ 6 dB (Section 7.8). A drone that is unsafe even at its defaults is not realistic. (Finding F3, decided in D-36: with the PX4 defaults this step kept no synthetic drone with $f_c \ge 10$ Hz in any of the 13 tested designs and priors, so $f_c$ is sampled in 3-10 Hz; real drones above 10 Hz are reported separately.)
4. **Uncertainty set of each drone** (used by the safety check, Section 7.8): the nominal plant $(b, \tau_m, T_d)$ plus the 8 corners $b(1\pm\delta_b)$, $\tau_m(1\pm\delta_\tau)$, $T_d + \{0, \Delta_d\}$. **$\delta_b = \delta_\tau$ = 20 % and $\Delta_d$ = 1 controller sample (D-36)**, set from the spread of the Tier 2 results (half-flight repeatability: ±20 % covers 17 of 18 changes at each drone's own $M_s$ peak; $T_d$ p90 1.3 samples). For a drone whose chip has a fitted low-pass term the delay step also holds the rest of the chip-delay range (D-33). Every plant of the set must be Nyquist-stable with $M_s \le M_{s,wc}$ = 3.0 (PM ≥ 19.2°, GM ≥ 3.5 dB), separately from the nominal limits (D-32, D-36).

### 7.2 Metrics

**Stability (maximum stability):**

- Crossover frequency $f_c$: where $|L(f_c)| = 1$.
- Phase margin: $PM = 180^\circ + \angle L(f_c)$.
- Gain margin: $GM = -20\log_{10}|L(f_{180})|$, where $\angle L(f_{180}) = -180^\circ$.
- Delay margin: $DM = \dfrac{PM\ [\text{rad}]}{2\pi f_c}$.
- **Peak sensitivity (modulus margin):** $M_s = \max_f \left|\dfrac{1}{1 + L(f)}\right|$. $1/M_s$ is the shortest distance from the Nyquist curve to the point $-1$, so it catches dangerous cases that PM and GM can miss. Limit $M_s \le M_{s,max}$ = 2.0 (6 dB) for the nominal plant (D-31); every plant of the uncertainty set: $M_s \le M_{s,wc}$ = 3.0 (D-32, D-36).
- **Several crossovers:** notch filters can make $|L|$ cross 1 (or the phase cross $-180^\circ$) more than once. Find **all** crossings on the frequency grid and use the **smallest** PM and GM.

**Delay (minimum delay):**

- Filter delay at crossover: $\tau_F = \dfrac{\varphi_{F}(f_c)}{2\pi f_c}$, where $\varphi_F(f) = -\angle F_g(e^{j2\pi f T_s})$ is the phase lag of the full gyro filter stack (lowpass + notches).
- D-term path delay $\tau_D$: the same formula with $F_g F_d$.
- Total loop delay: filter delay + ZOH + $T_d$ (for reports).

**Noise (minimum noise):**

- Motor-command noise caused by gyro noise with power spectral density $S_n(f)$:

$$N^2 = \int_{f_{lo}}^{f_{max}} \left|\frac{C_{fb}(f)}{1 + L(f)}\right|^2 S_n(f)\, df$$

  with $f_{lo} = \max(5 f_c, 20\ \mathrm{Hz})$ (D-36), so only noise above the control band counts and the band never leaves the frozen band of gate Q5 (20-780 Hz, D-23; the generator has no spectrum below 20 Hz). The upper limit $f_{max}$ = 780 Hz is the **same fixed value for all drones and logs** (D-23, gate Q5), because real logs have different sample rates. These are design choices: choose them once and keep them fixed. Always report noise relative to the default settings on the same drone and spectrum: $\tilde N = N / N_{default}$.
- **Noise with an uncertain spectrum:** a PSD estimated from a short window has random error. For the safety check, also compute $N_{upper}$ using the upper 90 % confidence bound of the PSD (Welch chi-squared factor, gate Q13).

**ESC-RPM notches on real logs (feasibility test 2026-10-10):** motor frequencies move by several Hz inside a window and the PX4 notches follow them. A notch fixed at the mean RPM over-predicts the remaining noise near the harmonics by up to 9 dB. Applying only the RPM notch bank in the time domain (following the logged RPM) and everything else in the frequency domain matches the logged filtered gyro, D-term input and torque within 1-2 dB (`noise_data.tracking_notch_psd`; decided as D-13, with a gate on the logged RPM rate).

Implementation: evaluate everything on one frequency grid, for example 2048 log-spaced points from 0.5 Hz to the Nyquist frequency of the loop plus dense points around each notch centre. Margins, $M_s$ and the Nyquist test use the whole grid; the noise integral uses only $[f_{lo}, f_{max}]$. Integrate with `numpy.trapezoid` (named `numpy.trapz` in NumPy 1.x), which works on non-uniform grids. Use numpy vectorization and no Python loops over frequencies.

**Modelling assumption to state in the paper:** the measured raw gyro spectrum is treated as sensor noise entering the loop. Part of it is real frame vibration, and this is a limitation.

### 7.3 Optimization problem

**Two scenarios:**

- **Scenario A, no ESC RPM telemetry (most public logs):** gyro lowpass + D-term lowpass + up to 2 notches at detected noise peaks (static or FFT-based; at a fixed operating point they are the same model). Motor frequencies are *estimated* from the spectrum peaks.
- **Scenario B, with ESC RPM telemetry:** gyro lowpass + D-term lowpass + ESC-RPM notch bank. Motor frequencies are *measured*: $f_{m,i}$ = RPM$_i$/60 from `esc_status` (Section 7.4.5). Exact frequencies allow narrow notches, which remove much noise for little delay. This is where the goal "minimum noise and minimum delay" gains the most.

Decision variables for the PX4 preset:

| Variable | PX4 parameter | Search range | Scenario |
|---|---|---|---|
| $f_g$ | `IMU_GYRO_CUTOFF` | 15 Hz to min(300 Hz, 0.45 x filter rate) | A, B |
| $f_d$ | `IMU_DGYRO_CUTOFF` | 10 Hz to min(200 Hz, 0.45 x filter rate) | A, B |
| $f_{0,k}, BW_k$ | `IMU_GYRO_NF0/NF1` | at detected peaks; BW 5-100 Hz (PX4 limit, D-16); on or off | A |
| $BW_{dnf}$ | `IMU_GYRO_DNF_BW` | 5-30 Hz | B |
| $H_{dnf}$ | `IMU_GYRO_DNF_HMC` | 1, 2, 3 | B |

**Three optimization modes:**

All modes share the **stability limits** $\mathcal{S}$: $GM \ge 6$ dB, $M_s \le M_{s,max}$ = 2.0 (D-31) and PM $\ge$ 30° (D-30) for the nominal plant, all checked at every crossover (Section 7.2). $\mathcal{S}$ also holds the D-36 worst-case limits for the 8 corner plants of the uncertainty set (D-37 (1)), so every optimum passes the safety check of Section 7.8 by construction; a reference setting that meets every limit is always a candidate, so the optimum is never worse than it. Search: coarse grid on the fast grids (500 stability points, 1 Hz noise grid, 24 × 18), every candidate checked and the refinement run on the full grids (D-37 (4)).

- **Mode A, maximum stability (minimum delay) at the same noise:** maximize $PM(\theta)$ subject to $\tilde N(\theta) \le 1$ and $\mathcal{S}$. Maximizing PM at fixed PID gains is the same as minimizing the filter delay $\tau_F$ at crossover.
- **Mode B, minimum noise at the same stability:** minimize $\tilde N(\theta)$ subject to $PM(\theta) \ge PM(\theta_{default})$ and $\mathcal{S}$.
- **Mode C, Pareto front:** sweep the noise limit $\tilde N_{max}$ from 0.25 to 2 and record the best PM (and its $\tau_F$) for each value, subject to $\mathcal{S}$.

**Solver:**

1. Coarse grid over all variables, fully vectorized (for example 40 x 30 x 6 x 3 points).
2. Take the best feasible grid point.
3. Refine the continuous variables with `scipy.optimize.minimize` (Nelder-Mead or SLSQP) while the discrete variables stay fixed.
4. Save $\theta^*$, $PM^*$, $GM^*$, $M_s^*$, $\tau_F^*$, $\tilde N^*$ and the solver time.

Check on about 20 cases with a very fine brute-force grid that the refinement finds the true optimum.

Operating points: start with hover only. If time allows, add a high-throttle point (motor frequencies scale up) and use the worst-case PM with the average noise.

### 7.4 Real noise data pipeline (public PX4 logs)

**Where:** PX4 Flight Review public logs (review.px4.io). Licence: **CC-BY** (PX4 maintainers, January 2025), so a derived spectrum library may be published with attribution.

**What we need:** logs that contain **raw high-rate gyro** data, the topic `sensor_gyro_fifo`. PX4 records it only when bit 8 of `SDLOG_PROFILE` is set.

#### 7.4.1 What the data audit found (2026-10-06)

| Fact | Value | Consequence |
|---|---|---|
| Public logs in the index (`https://review.px4.io/dbinfo`, gzipped JSON, about 32 MB) | 473,088 | Large pool |
| Real-hardware multirotor logs, at least 60 s, since 2021 | 182,945, from 23,556 `vehicle_uuid`s | Enough vehicles for a grouped split |
| Index fields | No topic list and no logging profile | Cannot select FIFO logs from the index: must screen file headers (Step B) |
| Random sample of 300 such logs with `sensor_gyro_fifo` | 23 (7.7 %, 95 % CI 5.2-11.2 %), all from different vehicles, mostly from 2026 | About 14,000 candidate logs. Risk R1 is low |
| Logs whose description mentions tuning or vibration | 21 of 120 (17.5 %) have FIFO | Keyword search helps a little |
| Size of FIFO logs | median 34 MB, max 265 MB | Download only after screening; delete after processing |
| Full pipeline on 4 FIFO logs | 2 clean (FIFO rate 2,000 and 6,400 Hz); 2 lost 49 % and 62 % of samples to logger dropouts | Data-quality gates are necessary (Section 7.4.3) |
| ESC RPM vs spectrum (2 clean logs) | Motors at 98-110 Hz (RPM/60), PSD peaks at 106, 206, 400 Hz; second log 117-133 Hz | Motor-harmonic noise model confirmed; RPM is a usable ground truth |
| Defaults stored in each log | Gyro-cutoff setup defaults of 40, 80 and 90 Hz; D-term default 30 Hz in v1.14-v1.16 | Read defaults per log (gate Q11) |
| Board rotation | `SENS_BOARD_ROT` = 4 and 8 in 2 of 4 logs | Rotate board axes to body axes (gate Q7) |

#### 7.4.2 Pipeline overview

```text
A. Index filter (dbinfo) --> B. Header screen (range request) --> C. Vehicle split 50/50
   --> D. Download fit-half logs, pilot study, freeze thresholds --> E. Download all, quality gates Q1-Q16
   --> F. Rebuild gyro, windows, PSD --> G. Extract flight-controller data (7.4.5) --> H. Go/no-go
```

**A. Index filter.** Download the index once (`curl -L https://review.px4.io/dbinfo`, gzipped JSON). Keep entries with `mav_type` in {Quadrotor, Hexarotor, Octorotor}, `sys_hw` not containing `SITL`/`SIM`, `source` not `CI`, `duration_s` $\ge$ 60, `log_date` $\ge$ 2021. Each entry has a `download_url` on `cdn.logs.px4.io`.

**B. Header screen (do not download whole logs blindly).** Read only the start of each candidate file with an HTTP range request (`Range: bytes=0-3000000`), streaming, and stop as soon as normal data messages begin. The ULog definitions section contains all parameters (including `SDLOG_PROFILE`) and the `add_logged_message` records list the topics being logged. Keep the log if `sensor_gyro_fifo` is logged (bit 8 set). Also record bits 3 and 4 (needed for Tier 2 and for E10/E11) and the filter, PID and DShot parameters. Tested on 420 logs on 2026-10-06; it reads about 0.3-3 MB per log instead of a median 34 MB. Be polite to the server: at most 4 parallel requests, a pause of at least 1 s per request, and a clear User-Agent. Code: `src/ulog_header.py` (parser) and `src/log_screen.py`; results: `data/screen/screen_results.jsonl` (CSV/JSONL/NPZ instead of parquet: no extra package needed).

**C. Split by vehicle BEFORE anything else:** 50 % for fitting (noise generator, clustering, pilot study, Tier 2) and 50 % held out as the real test set. Split by `vehicle_uuid`; for an empty uuid use the fallback key of gate Q14. Never use held-out vehicles to fit or tune anything, including the data-quality thresholds. This prevents data leakage, and reviewers check for it.

**D. Pilot study** on 20-30 fit-half logs to fix all **TBD** thresholds (Section 7.4.3), then freeze them (decision D-10).

**E-G.** Download all screened logs, apply the gates, build the spectrum library, extract the flight-controller data. Keep the `.ulg` files in `data/raw_logs/` until Phase 9 (decision D-22; risk R8).

**H. Go/no-go on Day 23 (2026-10-20, D-18):** after all gates, target at least 100 vehicles in total (fit + test); minimum 30. If not, use the fallbacks of risk R1 (Section 13).

Every gate is checked in code (`src/data_quality.py`), and every rejected log or window gets a reason code. **All TBD thresholds below were frozen on 2026-10-15 as decision D-23 (Section 2).** The paper reports a **data funnel table** (Table 1): how many logs and windows each gate removed. **TBD** values are fixed by the pilot study below.

**Pilot study to fix the TBD thresholds (Days 20-21, Oct 17-18, fit half only, 20-30 logs):**

1. **Dropout limit $D_{max}$:** take at least 5 clean logs. Insert artificial gaps that copy the real gap pattern (gap lengths from the bad logs) at increasing dropout fractions. Because PSDs are never computed across gaps, gaps only reduce the number of averages. Compare band powers with the clean result. $D_{max}$ = the largest fraction where the median band error stays below **TBD** dB (candidate 1 dB) and enough segments of length $L_{min}$ remain.
2. **Frequency range $f_{max}$:** make a histogram of $f_s$ over the accepted logs. $f_{max}$ = the largest value for which at least **TBD** % (candidate 90 %) of logs satisfy $0.8 \cdot f_s/2 \ge f_{max}$. Check with the RPM logs that the motor harmonics that matter for the filters (at least up to the 3rd) lie below $f_{max}$. $f_{min}$: the lowest frequency where the spectrum is dominated by vibration rather than flight motion (inspect the plots), and below $5 f_c$ of all modelled drones.
3. **Window length $W$ and `nperseg`:** inside the same steady flight, compare band powers from 5, 10 and 20 s windows. $W$ = the shortest window whose band powers stay within **TBD** dB of the 20 s estimate. Then choose `nperseg` so that each window gives at least the minimum number of averages.
4. **Steady-flight limits:** plot the distributions of rate-setpoint activity and throttle change. Choose limits that remove clear manoeuvres but keep at least **TBD** % of the airborne time.
5. **Jitter and clipping:** count them; they are usually rare. Choose conservative limits.
6. **Freeze:** write all chosen numbers into Section 2 as a new decision, then process all logs (both halves) with exactly these numbers.

#### 7.4.4 Rebuild the gyro signal and compute spectra

1. **Fields** (checked 2026-10-06 in PX4 `msg/SensorGyroFifo.msg`): `timestamp`, `timestamp_sample`, `device_id`, `is_external`, `dt` [µs], `scale` [rad/s per count], `samples`, `x[32]`, `y[32]`, `z[32]` (int16). Angular rate = count $\times$ `scale`.
2. Concatenate the first `samples` values of each message. Sample times: `timestamp_sample` is the time of the last sample in the message (**checked 2026-10-14** in the PX4 v1.16.0 ICM-42688-P driver: data-ready time of the newest sample, or the read time when polled; `notes/px4_notes.md`). **Found 2026-10-10:** `timestamp_sample` jitters by up to about ±1 sample between messages, so find gaps per message (break where the timestamp moves more than 3 samples away from the sample count) and fit one straight line of sample times per gap-free segment. The fitted IMU rate differs from the nominal `1e6/dt` (6,387.6 instead of 6,400 Hz; in the pilot logs that pass $D_{max}$: 2 kHz IMUs −0.30 to +0.03 %, 6.4 kHz −0.19 to +0.62 %, 8 kHz −1.0 to +1.5 %, one IMU −3.0 %): use the measured rate for the PSD frequency axis (gate Q6). **Corrected 2026-10-15:** the earlier figure "2,015 instead of 2,000 Hz" came from log b4a9719c with 63 % dropout, where the measured rate is not reliable; up to 20 % dropout it agrees with a single long-segment fit within 0.006 %.
3. Apply gates Q4-Q9: gap-free segments, rotation to body axes, instance choice, clipping.
4. Select steady windows (gate Q10).
5. Welch PSD per axis (`scipy.signal.welch`, Hann window, `nperseg` from the pilot), only inside gap-free segments, then average.
6. Detect noise peaks (`scipy.signal.find_peaks` on the log-PSD, prominence **TBD**).
7. Save to `data/spectra/`: the PSD on the fixed band $[f_{min}, f_{max}]$ and the metadata: log id, vehicle key, split (fit or test), hardware, IMU `device_id`, $f_s$, firmware version, window times, $\theta_{actual}$, $\theta_{default}$, PID gains, per-motor RPM (mean and spread in the window), flags (`has_rpm`, `has_highrate`, `has_sysid`), dropout fraction, gate results, licence.

#### 7.4.5 Using the flight-controller data in each log

Every ULog stores **all** flight-controller parameters, and many logs store extra topics. Using them makes the thesis much stronger: the real logs then give not only real noise, but also real settings, real controllers, measured motor speeds and measured filter outputs.

| Data | Where in the log | How we use it | What it strengthens |
|---|---|---|---|
| Real filter settings | `IMU_GYRO_CUTOFF`, `IMU_DGYRO_CUTOFF`, `IMU_GYRO_NF*`, `IMU_GYRO_DNF_*`, `IMU_GYRO_RATEMAX` | **RQ1 on real settings:** for each real window compare $\theta_{actual}$ (what the pilot flies), $\theta_{default}$ and $\theta^*$ on the same real noise. Figure: what pilots really use (audit: gyro cutoff 40 Hz in 56 % of logs; 30, 80, 20, 15 Hz common; dynamic notch off in about 80 %) | C2, RQ1 |
| Real PID gains | `MC_ROLLRATE_P/I/D/K`, `MC_PITCHRATE_*` | Real-gain drones (Tier 3, option b); needed for E10, E11 and the Tier 2 realism check | Realism of RQ1-RQ2 |
| **ESC RPM** | `esc_status.esc[i].esc_rpm` (also `esc_voltage`, `esc_current`) | See the steps below | Scenario B, E13 |
| Filtered gyro at full rate | `vehicle_angular_velocity` (profile bit 4) | **E10:** validate the filter model on real data (method below) | C1 |
| Controller output at full rate | `vehicle_torque_setpoint` (bits 3/4), `actuator_motors` | **E11:** validate the noise metric (method below); Tier 2 system identification | C1, plant realism |
| Onboard FFT peaks | `sensor_gyro_fft` (when `IMU_GYRO_FFT_EN` = 1) | Compare PX4's own peak frequencies with ours. Supports the claim that a drone can compute the safety-check inputs onboard | Deployment claim |
| Operating point | `battery_status` voltage, `MPC_THR_HOVER`, mean of `actuator_motors` | Metadata. Show how motor frequency and noise move with battery voltage and throttle; this supports the motivation for in-flight retuning | Motivation |
| Vibration metrics | `vehicle_imu_status` | Sanity check: our noise levels should rank vehicles in a similar order | Data quality |

**How to use ESC RPM properly:**

1. **Validity checks:** RPM > 0 for all motors in the window; the number of reporting motors equals the motor count; note the update rate (4 Hz and 200 Hz seen in pilot logs; both are fine for steady windows); record the RPM source (DShot telemetry, bidirectional DShot `DSHOT_BIDIR_EN`, DroneCAN/UAVCAN).
2. **Unit check:** confirm that `esc_rpm` is mechanical RPM by matching RPM/60 with the fundamental noise peak (it matched in both pilot logs). If a vehicle is off by an integer factor (motor pole pairs), correct it or set `has_rpm = False` (gate Q16). **VERIFY** for each ESC type.
3. **Use 1, better noise model:** in the parametric noise model (Section 7.5), fix the motor frequencies $f_{m,i}$ to the measured values. This leaves fewer free parameters and gives better fits, and it shows how the harmonic amplitudes $A_h$ depend on the harmonic number $h$, which improves the generator.
4. **Use 2, Scenario B real test set:** real noise plus real RPM lets us test RPM-notch-bank tuning on real data.
5. **Use 3, accuracy of Scenario A (E13):** estimate the motor frequencies from the spectrum only, as if no RPM existed, and compare with the RPM truth. Report the error in Hz. This shows how much the "minimum delay" result depends on having RPM telemetry.
6. **Use 4, ML input:** in Scenario B, the motor frequencies (mean and spread over the motors) are input features (Section 7.7).
7. **Use 5, operating point:** RPM versus battery voltage and throttle shows how fast the noise moves during a flight.
8. **Caution:** RPM logs are a minority (`DSHOT_BIDIR_EN` = 1 in 9 of 91 logs that have this parameter; 8 of 19 among FIFO logs). Report Scenario B results separately and do not over-claim.

**E10, filter-model validation on real logs** (logs with FIFO and full-rate `vehicle_angular_velocity`):

1. Take the same steady window from both topics.
2. Predict the filtered spectrum from the raw spectrum and the log's own filter settings: $S_{pred}(f) = |F_g(f;\ \theta_{actual})|^2\, S_{raw}(f)$. If the filtered signal is published at a lower rate than the filters run, fold (alias) the predicted spectrum down to the publication rate. Include dynamic notches if enabled, placed at the logged RPM or onboard FFT peaks.
3. Compare with the measured PSD of `vehicle_angular_velocity` from $f_{lo}$ to half the publication rate; report the error in dB per band.
4. This directly tests contribution C1 on real data, and it answers the VERIFY item about the filter sample rate (try both rates and see which one matches).

**E11, noise-metric validation on real logs** (logs with FIFO and full-rate `vehicle_torque_setpoint`):

1. Above about $5 f_c$ the loop gain is small ($|L| \ll 1$), so $1/(1+L) \approx 1$, and the controller output caused by gyro noise is the noise passed through $C_{fb}$.
2. Predicted torque-setpoint spectrum: $S_{u,pred}(f) = |C_{fb}(f;\ \text{real gains},\ \theta_{actual})|^2\, S_{raw}(f)$. This needs **no plant model**, only the log's own PID gains and filter settings.
3. Compare with the measured PSD of the roll torque setpoint above $f_{lo} = \max(5 f_c, 20\ \mathrm{Hz})$ (D-36); report the error in dB.
4. This validates the noise metric $N$ that every optimization mode uses.

### 7.5 Noise archetypes and synthetic noise generator (unsupervised ML)

**Clustering finds typical noise types:**

1. Feature vector per spectrum: $\log_{10}$ PSD in 48 log-spaced bands from $f_{min}$ to $f_{max}$ (the fixed band of gate Q5, the same for every log), mean-removed. Never "to Nyquist": Nyquist differs between logs.
2. PCA (`sklearn.decomposition.PCA`), keeping about 95 % of the variance.
3. k-means (`sklearn.cluster.KMeans`), choosing $k$ between 2 and 8 by silhouette score.
4. Plot the cluster centroids and name them, for example "clean", "motor-peak dominated", "frame resonance", "broadband".
5. Cross-tabulate clusters against IMU chip, sample rate and firmware version (gate Q12). Clusters must describe noise physics, not hardware labels.

**Parametric noise model, fitted to each real spectrum:**

$$S_n(f) = \sigma_w^2 + \sum_{i=1}^{4}\sum_{h=1}^{H} \frac{A_h}{1 + \left(\frac{f - h f_{m,i}}{\gamma_h}\right)^2} + \sum_{r} \frac{A_r}{1 + \left(\frac{f - f_r}{\gamma_r}\right)^2}$$

The three parts are a broadband floor, motor harmonic peaks, and frame resonance peaks. Fit with `scipy.optimize.least_squares` on the log-PSD, on the fixed band only. Start the peak positions from `scipy.signal.find_peaks`. **When ESC RPM is available, fix $f_{m,i}$ to the measured RPM/60** instead of fitting them (Section 7.4.5, use 1). Report the fit error per spectrum and drop spectra the model cannot fit (error above **TBD** dB).

**Generator:** for each cluster, fit a simple distribution to the fitted parameters, for example a Gaussian on the log-parameters. Sample new parameter sets to create new realistic spectra. For the FPV extension, scale motor frequencies into the FPV range.

**Sanity check:** synthetic spectra must look like real ones. Compare statistics and centroid plots.

#### 7.5.1 Phase 3 results (2026-10-16; fit half for every choice, test half only processed)

- **Data:**
  - Screen of the first 4,327 vehicles of the D-21 order: 272 with raw gyro FIFO (6.3 %).
  - 216 vehicles with a board ID: **111 fit / 105 test**.
  - Usable after all gates (and the D-24 fallback): **52 fit-half vehicles (142 windows) and 43 test-half vehicles (112 windows): 95 in total.**
  - Most losses are logger dropouts (Q4: 44 fit, 41 test).
- **No stable noise types:**
  - PCA + k-means on one spectrum per vehicle, chip roll-off divided out: silhouette 0.26, bootstrap ARI 0.57. That fails the D-24 P3 rule (≥ 0.5 and ≥ 0.8).
  - The only stable split (ARI 0.84) is the IMU chip: ICM-42688-P/42686-P drones lose about 3 decades of noise above 500 Hz on the chip itself. That is a hardware label, not a noise type (gate Q12).
  - **So one generator for all spectra, with the chip as a covariate.**
- **Parametric model:**
  - fixed robust spline floor;
  - Lorentzian peaks, with motor harmonics at RPM/60 where valid;
  - one low-pass magnitude per chip model, kept only if the BIC gain is at least 10.
  - Median fit error **3.31 dB** (Welch noise 0.36 dB); 2 of 52 spectra dropped (> 5 dB).
- **Generator verdict:**
  - The floor is a Gaussian per chip class; peak sets are resampled whole from real vehicles, with jitter.
  - A classifier cannot tell synthetic from real spectra: cross-validated **AUC 0.495** (absolute levels), 0.47 (shapes).
  - **Leave one vehicle out** (equal sample sizes): nearest synthetic 8.36 dB vs nearest real 8.24 dB, so it generalises about as well as a new real drone.
- **Limitations** (to be stated in the paper):
  1. A remaining **+4.4 dB bias at 20-100 Hz** for non-ICM chips (median synthetic vs real; ICM-4268x +1.2 dB).
  2. **About 3 dB model misfit at the motor band** (95-130 Hz): several motors at slightly different, changing speeds make wider or split peaks than one Lorentzian.
  3. The frequency jitter (0.65 %) rests on only **4 drones** with valid RPM and at least 2 windows. The synthetic peak sets are therefore near-copies of real ones; only the floor is a new draw.
  4. **Small chip groups:** IIM-42652 and IIM-42653 have 2 vehicles each, ICM-42686-P 3. Their low-pass terms are weakly supported. Also, BIC treats Welch bins as independent, which inflates the gains.
- **Also recorded:**
  - The chip low-pass corner and order are not identifiable, so the ICM chip delay enters the loop model as a T_d uncertainty (D-25; VERIFY datasheet).
  - 3 test vehicles were lost only to the Q7 axis rule (rotations 6, 8, 12; too few long gap-free pieces). The rule was not changed after seeing the test half.
- **Quality:**
  - Mutation checks: clustering 10/10, generator 14/14, Jacobian 3/3.
  - The independent code review (2026-10-16) found no critical or high defects. Its 2 medium findings (overstated generator-realism claims) and 4 low findings are fixed or stated.

### 7.7 The ML tuner (supervised learning)

**Inputs (features):**

- noise: log-PSD in 32-48 bands on the fixed band $[f_{min}, f_{max}]$; frequency and height of the 3 largest peaks; broadband floor;
- drone and loop: filter rate, control rate, unfiltered crossover $f_c$, $\tau_m$, $T_d$, ratio $r$;
- scenario flag (A or B); in Scenario B the measured motor frequencies from ESC RPM (mean and spread over the motors, Section 7.4.5).

**Outputs:** $\theta^*$. Continuous values are predicted as $\log(f)$ (regression). The harmonic count is predicted as a class (classification). Train one model per optimization mode.

**Models:**

| ID | Model | Role |
|---|---|---|
| B0 | Firmware defaults | Baseline |
| B1 | Simple heuristic: gyro cutoff = 0.5 x lowest large noise peak; D cutoff = 0.5 x gyro cutoff | "Hobby rule" baseline |
| B2 | k-nearest neighbours regression (k = 5) | ML baseline |
| B3 | Ridge (linear) regression | ML baseline |
| M1 | Gradient boosting (`GradientBoostingRegressor` or LightGBM) | Main model |
| M2 | Small neural network (`MLPRegressor`, 2 hidden layers of 32-64 ReLU units) | Main model, easy to export to C |

**Training protocol:**

- Standardize inputs with `StandardScaler` inside a `Pipeline`.
- Split synthetic data 70/15/15 **grouped by drone id** (`GroupShuffleSplit`), so no drone appears in both train and test.
- Tune a few hyperparameters with `RandomizedSearchCV` and `GroupKFold` (5 folds). Keep the search small: at most 30 configurations per model.
- Fix random seeds. Save trained models with `joblib`.

**Evaluation on the synthetic test set AND on the real held-out test set.** For real spectra, the true label comes from running the optimizer on that real spectrum. The real test set has three parts: (1) real noise with synthetic drones, (2) real noise with the log's real PID gains (real-gain mode, Tier 3 b), (3) the Scenario B subset with real RPM. Report them separately.

- **Regret:** $\Delta PM = PM(\theta^*) - PM(\hat\theta)$ in degrees. Report median and 95th percentile.
- **All three goals (rule of Section 7.0):** $\tilde N(\hat\theta)$, $\tau_F(\hat\theta)$ and PM, GM, $M_s$ for every model and baseline, including $\theta_{actual}$ (what the pilot flew) on real logs.
- **Violation rate:** the share of predictions that break the noise limit or any stability limit $\mathcal{S}$ (Section 7.3), nominal and worst case, before and after the safety check.
- Parameter error as a percentage of the optimal value (secondary).
- Time per prediction compared with time per optimizer run.

### 7.8 Physics safety check

**Goal.** The ML model proposes; the physics model verifies. A setting leaves the check only if it is stable with margin and not noisier than allowed, for the nominal drone **and** for every nearby plant in its uncertainty set. Otherwise the check repairs it with as small a change as it can find, or falls back to a known-safe setting. "Safe" always means "safe within the model"; Section 7.11 and experiments E10-E11 test the model itself.

**Inputs:**

- $\hat\theta$: the ML prediction.
- $S_n$: the noise spectrum (offline: from the log; on a drone: from the onboard gyro FFT, which PX4 already has) and its 90 % upper bound $S_n^{up}$ (gate Q13).
- The drone model: nominal plant $p_0$ and the uncertainty set $\mathcal{P}$ = $p_0$ plus 8 corners (Section 7.1.1, Tier 3, step 4).
- $\theta_{ref}$: a known-safe reference setting, normally the drone's default $\theta_{default}$ (or the setting it is flying now).
- Limits:

| Limit | Symbol | Value |
|---|---|---|
| Noise | $\tilde N_{max}$ | 1 in Mode A (not noisier than the default); the chosen limit in Modes B and C |
| Phase margin floor | $PM_{min}$ | **30°** for the nominal plant (D-30) |
| Gain margin | $GM_{min}$ | 6 dB for the nominal plant |
| Peak sensitivity | $M_{s,max}$ | **2.0** (6 dB) for the nominal plant (D-31) |
| Worst-case peak sensitivity | $M_{s,wc}$ | **3.0** for every plant of $\mathcal{P}$ (D-32, D-36): Nyquist-stable, $M_s \le 3.0$, PM $\ge 2\arcsin(1/(2M_{s,wc}))$ = 19.2°, GM $\ge M_{s,wc}/(M_{s,wc}-1)$ = 1.5 (3.5 dB) |
| Delay (Mode B only) | $\tau_{max}$ | $\tau_F(\theta_{ref})$: not more filter delay than the reference |

**Step 1, hard limits (projection).** Clip every parameter to its legal range: $f_g$, $f_d$ at most 0.45 $\times$ filter rate and inside the PX4 parameter bounds; notch centres inside [`IMU_GYRO_DNF_MIN`, 0.45 $\times$ filter rate]; notch bandwidths inside their ranges (Section 7.3); harmonic count rounded to an integer 1-3. A filter outside these ranges is not even defined, so this step comes first.

**Step 2, stability test with the Nyquist criterion (for every plant in $\mathcal{P}$).** Margins alone can mislead when notch filters create several crossovers. Our open loop $L$ contains one integrator and is otherwise stable (filters, motor lag and delay are all stable). For such a loop the Nyquist criterion says: **the closed loop is stable if and only if the Nyquist curve of $L$ does not encircle the point $-1$.** Practical test: find every frequency where the curve crosses the negative real axis to the left of $-1$ (phase $= -180^\circ \pm k \cdot 360^\circ$ while $|L| > 1$). Give each crossing $+1$ or $-1$ according to its direction. The sum must be 0. For a simple loop this reduces to "GM > 0 dB". Check the code with unit tests on known stable and unstable textbook loops, and once against the closed-loop poles of a single-rate discrete-time model (`python-control`).

**Step 3, margins and limits (D-32: the nominal limits for the nominal plant, separate worst-case limits for every plant in $\mathcal{P}$):**

- nominal plant $p_0$: PM at **every** gain crossover $\ge PM_{min}$, GM at **every** phase crossover $\ge GM_{min}$, $M_s \le M_{s,max}$;
- every plant in $\mathcal{P}$ (worst case counts): $M_s \le M_{s,wc}$ with the PM and GM it guarantees (PM $\ge 2\arcsin(1/(2M_{s,wc}))$, GM $\ge M_{s,wc}/(M_{s,wc}-1)$, at every crossover);
- noise $\tilde N(\theta)$ computed with the upper-bound spectrum $S_n^{up}$ $\le \tilde N_{max}$, so a short or noisy spectrum estimate cannot fool the check;
- in Mode B also $\tau_F(\theta) \le \tau_{max}$.

**Step 4, accept or repair.** If $\hat\theta$ passes steps 2-3, return it unchanged. Otherwise search on the straight line between $\hat\theta$ and $\theta_{ref}$ in log-parameter space:

$$\theta(\lambda) = \exp\big((1-\lambda)\log\hat\theta + \lambda \log\theta_{ref}\big), \qquad \lambda \in [0, 1]$$

Discrete parts (harmonic count, notch on/off) take the values of $\theta_{ref}$ during the repair.

1. First check that $\theta_{ref}$ itself passes. If it does not, return $\theta_{ref}$ with the flag "reference unsafe" and count these cases (they say something about the defaults). Real drones whose flown setting is flagged stay in the test set and are reported as a finding (D-36 (2)); on the fit half 10 of 28 identified flown settings are flagged (5 fail nominally, 5 only in the worst case).
2. Coarse scan: $\lambda = 0, 1/8, 2/8, \dots, 1$. Take the first $\lambda$ that passes.
3. Bisection between the last failing and the first passing $\lambda$, 5 steps (resolution 1/256).
4. Return $\theta(\lambda)$.

Why this is better than the earlier "±5 % steps" loop: it **always** ends with a passing setting (because $\theta_{ref}$ passes), it needs a fixed number of evaluations (at most 9 + 5 = 14), and it keeps as much of the ML improvement as it can. Honest limitation: feasibility along the line need not be monotone, so the result is guaranteed safe but not guaranteed to be the smallest possible change.

**Step 5, output.** Return $\theta_{safe}$, $\lambda$ (0 = ML prediction untouched, 1 = fell back to the reference), worst-case PM, GM, $M_s$, $\tilde N$, $\tau_F$, and a flag. Log everything.

**Step 6, cost on a microcontroller.** Cost = grid points $\times$ plants (9) $\times$ evaluations (at most 14) $\times$ cost of one filter-stack evaluation. Report the PC time and a Cortex-M7 estimate (Section 7.10). If it is too slow: use fewer plants (the nominal plus the 2 corners that are worst most often, found offline) or a smaller grid (then step 7c matters more).

**Step 7, offline verification for the paper:**

1. Time-domain simulation (Section 7.11) of accepted settings for a random subset, each also with its worst-case plant: no growing or sustained oscillation; overshoot within **TBD**.
2. Violation rate with a confidence bound: evaluate $n$ held-out cases on the dense grid. If there are 0 violations, the true violation rate is below $3/n$ with 95 % confidence (the "rule of three"); with $k > 0$ violations use the Clopper-Pearson bound (`scipy.stats.binomtest(k, n).proportion_ci()`). Example: $n$ = 3,000 gives a bound below 0.1 %. The idea follows Hertneck et al. 2018 (Section 16).
3. Grid check: compare the coarse onboard grid (for example 64 points) with the dense grid. Report the largest difference in PM, GM, $M_s$ and $\tilde N$, and add it as an extra margin to the onboard limits.
4. Report how often $\hat\theta$ passes untouched, the distribution of $\lambda$, the regret left after repair, and how often the fallback was used.

**Step 8, rules for in-flight use** (describe as future work; do not build): change settings only in steady flight; limit the rate of change (at most **TBD** % per second) and use hysteresis so settings do not switch back and forth; keep the last accepted setting when the onboard spectrum is unreliable (too few FFT averages).

```text
input : theta_hat (ML), spectrum S_n and upper bound S_up, plant set P (nominal + 8 corners),
        theta_ref (known-safe reference), limits N_max, PM_min, GM_min, Ms_max, Ms_wc (D-32)
theta_hat = project_to_bounds(theta_hat)                         # step 1

function passes(theta):
    for p in P:                                                   # robust: every plant counts
        L = open_loop(theta, p)                                   # on the frequency grid
        if not nyquist_stable(L):          return False           # step 2
        lim = nominal_limits if p is p0 else worst_case_limits(Ms_wc)   # step 3 (D-32)
        if min_PM(L) < lim.PM:             return False           # all crossovers
        if min_GM(L) < lim.GM:             return False
        if Ms(L) > lim.Ms:                 return False
    if N_rel(theta, S_up) > N_max:         return False           # noise with upper-bound spectrum
    return True

if passes(theta_hat):      return theta_hat, lambda = 0           # accepted unchanged
if not passes(theta_ref):  return theta_ref, flag = "reference unsafe"
blend(l) = exp((1 - l) * log(theta_hat) + l * log(theta_ref))   # discrete parts from theta_ref
k  = first k in 1..8 with passes(blend(k / 8))                    # coarse scan, step 4.2
lo = (k - 1) / 8;  hi = k / 8
repeat 5 times:                                                   # bisection, step 4.3
    mid = (lo + hi) / 2
    if passes(blend(mid)): hi = mid  else: lo = mid
return blend(hi), lambda = hi                                     # step 5
```

**How the check serves the goal:** steps 2-3 enforce the stability limits robustly (maximum stability), the noise test enforces the noise limit (minimum noise), and the repair keeps as much of the ML model's delay reduction (minimum delay) as safety allows.

    **Limitations from the independent review of branch `phase4`** (the reviewer's 10 declined points; all stand as limitations, D-34; author 2026-10-18), one sentence each, in the reviewer's numbering:
    1. **Shared feedback bias (D-14):** in Position and auto modes a plant identification is accepted when the rate-setpoint and attitude-setpoint instruments agree, but agreement cannot reveal a feedback bias that both instruments share, so these identifications may carry a common closed-loop bias.
    2. **Interior worst case, no μ-analysis:** robustness is checked only at the nominal plant and the 8 corners of the ($b$, $\tau_m$, $T_d$) box; with notch filters in the loop the worst plant can lie inside the box, so the worst-case margins may be slightly optimistic, and no structured-singular-value (μ) analysis was done.
    3. **The worst-case limit is a convention:** $M_{s,wc}$ = 3.0 (D-32, D-36) lies midway between the textbook "less than about 2" and "larger than about 4 ... poor robustness" (Skogestad and Postlethwaite 2005) without a source of its own, and the share of real flown settings flagged "reference unsafe" depends on it (fit half: 22 % of the nominal passes at 3.0, 4 % at 3.5, 0 % at 4.0).
    4. **Fig. 1 filter rate:** Fig. 1 is computed at the loop model's filter rate of 6,400 Hz although 2 kHz is the most common FIFO rate in the data; at 2 kHz the delay curves in the crossover band change by at most 0.16 ms in panel (a) and 0.19 ms in panel (b) (D-term path).
    5. **In-place mutation testing:** the mutation checks that prove the tests' sensitivity rewrite a source file, run the tests and restore it byte-identically (180 s timeout per mutant), so an interrupted run would leave a mutated file in the working tree until the git check after the run.
    6. **Mixed airframes and firmware in the real set:** the identified real drones include one FPV airframe (d32cc24c) and PX4 v1.17 logs evaluated with the v1.16 filter model (the filter structure is the same), so the real set is not a clean sample of large v1.16 drones.
    7. **Rate statistic:** the count of fit logs whose controller rate is more than 5 % away from `IMU_GYRO_RATEMAX` (42 of 102) includes one log whose setting is 0 (no valid setting; measured 795 Hz).
    8. **Frequency-domain identification gates:** Tier 2 fits are accepted by frequency-response gates (fit error ≤ 3 dB / 15°, frozen in D-36) instead of the held-out VAF gate first planned in Section 7.1.1, so the identified plants are judged in the frequency domain only, without a held-out time-domain prediction check.
    9. **Run time of the identification code:** `body_rate_on_grid` re-filters a whole gap-free segment for every piece; this costs run time only and changes no result.
    10. **Held skipped publications:** skipped controller publications (up to 8 in a row) are bridged by holding the last command, on the assumption that the motor command holds its value during the pause; the reviewer accepted this because the other logged topics skip together, so it is a stated assumption, not a measurement.

    **Further limitations from the Phase 4 decisions (D-36):**
    - **Scenario B rests on few sources:** only 5 of the 50 generator entries carry motor harmonics, so synthetic Scenario B drones (about 10 % of a training set when sources are drawn uniformly) repeat 5 peak sets, and the real Scenario B test set is small (about 5 test-half vehicles with valid RPM, estimated); Scenario B results are reported separately and not over-claimed.
    - **Training crossover range:** synthetic drones cover $f_c$ = 3-10 Hz only, because no synthetic drone with $f_c \ge 10$ Hz passes the limits at the PX4 defaults; real drones above 10 Hz (2 of the 26 fit-half real-gain cases by the unfiltered crossover, 3 by the flown one; test half 3 and 5) and the 4 test-half cases below 3 Hz lie outside the training range and are reported separately (D-37 (5), D-39 (1)).
    - **Coverage gap at high crossover:** the kept synthetic population has only 1.7 % of its drones at 8-10 Hz (17 of 1,000, measured in Task 3; the planning run gave the same), while 5 of the 26 real fit-half real-gain cases sit there, so the synthetic-vs-real comparison has a coverage gap at high crossover. It follows from F3: no synthetic drone with $f_c \ge 10$ Hz is safe at the PX4 defaults, and few between 8 and 10 Hz are.
    - **Two numbers for "reference unsafe" (D-37 (7)):** 22 % of the nominally passing flown settings fail the worst case (5 of 23). Separately, 36 % of all flown settings are "reference unsafe" (10 of 28), and 35 % in the Task 3 set (9 of 26, b79d2e3d excluded).

    **Findings of the held-out test half (Task 3; reported as findings, not limitations, D-39 (2)):**
    - **More nominally unsafe flown settings:** 9 of the 28 test-half flown settings (32 %) fail the nominal limits, against 5 of 26 (19 %) on the fit half.
    - **Scenario B:** all 4 test-half Scenario B cases (4695924f and b98012f4, roll and pitch) fail the nominal limits.
    - **Three extreme cases:** c6f66b3d roll (PM 17.4°, $M_s$ 9.25), d10980b0 roll (PM 21.4°, $M_s$ 3.91) and b98012f4 pitch (PM 15.2°, $M_s$ 4.88) are implausible for drones that fly, which points to wrong single identifications (F5) or to the limits of the model.
    - **Unmodelled filter:** 6 test-half cases fly the FFT dynamic notch, which the loop model does not include.
    - **Effect on RQ1:** these findings do not invalidate the RQ1 result. They inflate the all-case ΔPM of the test half (+4.5°), while the "safe references only" column of Table 2 (Section 7.3.1) gives a median ΔPM of **+2.1°** on the test half, the honest held-out number for well-tuned drones.

## 15. Glossary

- **Gyroscope (gyro):** sensor that measures rotation rate.
- **PSD (power spectral density):** how much noise power is at each frequency.
- **Lowpass filter:** passes low frequencies and removes high ones. The **cutoff** is where it starts to cut (-3 dB).
- **PT1 / PT2 / PT3:** a first-order lowpass filter, or 2 or 3 of them in series.
- **Butterworth filter:** a smooth lowpass filter; PX4 uses the 2nd-order version.
- **Notch filter:** removes a narrow band around one frequency. **Q** is its sharpness: higher Q means narrower.
- **RPM filter / ESC notch:** notch filters that follow each motor's measured speed.
- **Dynamic notch (FFT):** a notch placed at the biggest noise peak found by an onboard FFT.
- **Bode plot:** magnitude and phase of a system plotted against frequency.
- **Crossover frequency:** where the open-loop gain equals 1.
- **Phase margin (PM):** how much extra phase lag the loop can take before it becomes unstable.
- **Gain margin (GM):** how much extra gain the loop can take before it becomes unstable.
- **Delay margin:** how much extra time delay the loop can take.
- **ZOH (zero-order hold):** a digital controller holds its output constant for one period.
- **ULog:** PX4's log file format (`.ulg`).
- **Amortized optimization:** training a model to output an optimizer's answer directly, so the optimization does not need to run again each time.
- **Regret:** how much worse the ML prediction is than the true optimum.
- **Data leakage:** test information accidentally entering training, which makes results look better than they are.
- **PCA:** reduces many features to a few main directions. **k-means:** groups similar items together.
- **Gradient boosting:** many small decision trees added together. **MLP:** a small fully-connected neural network.
- **TinyML:** running ML models on microcontrollers. **Quantization:** storing numbers with fewer bits, for example int8.
- **MAC:** one multiply-accumulate operation, a measure of neural-network compute.
- **Logger dropout:** a period where the flight controller could not write all data to the SD card, so samples are missing from the log.
- **Nyquist frequency:** half the sample rate, the highest frequency a sampled signal can represent. A 2 kHz gyro cannot show noise above 1 kHz.
- **Nyquist criterion:** a test of closed-loop stability from the open-loop frequency response: the loop is stable when the curve of $L$ does not encircle the point $-1$ (for our loops).
- **Peak sensitivity $M_s$ (modulus margin):** the largest value of $|1/(1+L)|$; $1/M_s$ is the closest distance of the Nyquist curve to $-1$. Smaller $M_s$ means more robust.
- **System identification:** estimating model parameters (here $b$, $\tau_m$, $T_d$) from measured input and output signals.
- **Uncertainty set:** a small set of plant models around the nominal one (here 8 corners) used to check that a setting is safe even if the plant is slightly different.
- **Bisection:** finding a boundary by halving an interval again and again.
- **ESC RPM telemetry:** motor speed reported back by the motor controllers (ESCs), for example through bidirectional DShot.
- **Default parameter (ULog):** the value a parameter would have without user changes; a ULog file stores it when it differs from the configured value.
